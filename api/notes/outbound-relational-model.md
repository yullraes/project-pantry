# 출고 논리 데이터 모델 초안

## 근거와 범위

`outbound-plan-report-data-propositions.md`의 명제를 릴레이션으로 옮긴다. 이 문서는 사람용 기획 초안이며 현재 구현 계약이나 실행할 데이터베이스 마이그레이션이 아니다.

합의된 관계와 조건부 설계를 구분한다. 명제 문서의 미정 사항을 테이블 구조만으로 확정하지 않는다.

- 예정 없이 완료 보고를 기록할 수 있다.
- 예정 한 건에는 논리적 완료 보고가 최대 하나 연결된다.
- 예정 수량과 실제 수량의 차이는 미납 잔량으로 이월하지 않는다.
- 추가 납품은 별도의 논리적 보고다.
- 아래 보고 판 구조는 입고와 같은 추가 전용 정정 방식을 채택한다는 조건부 설계다.
- 납품 수량과 반출 내역의 분리는 식당 인계까지 보고한다는 현재 초안을 따른다. 창고 반출까지만 보고하기로 하면 구조를 재검토한다.

상품·식당·위치는 다른 영역의 기준 정보를 참조한다. 아래 `products`, `restaurants`, `locations`는 논리적 참조 이름이며 기존 코드나 실제 테이블 이름을 확정하지 않는다. 담당자 식별값은 입고 초안처럼 문자열로 표현한다.

## 관계 개요

```text
outbound_plans 1 ── N outbound_plan_items
       0..1
        │
       0..1
outbound_reports 1 ── N outbound_report_revisions
                              1
                              │
                              N
                     outbound_report_items
                              1
                              │
                              N
                     outbound_withdrawal_items
```

예정 한 건은 완료 보고가 없거나 하나 있다. 완료 보고 한 건은 예정이 없거나 하나를 참조한다. 정정 판은 별도의 완료 보고 건이 아니다.

## 1. outbound_plans

술어:

> 담당자 `created_by`가 시각 `created_at`에 식당 `restaurant_id`를 대상으로 하는 납품 예정 `id`를 등록했다.

| 열 | 형식 | NULL | 의미 |
| --- | --- | --- | --- |
| id | BIGINT | 불가 | 납품 예정 식별자 |
| restaurant_id | BIGINT | 불가 | 예정 납품처 |
| created_by | VARCHAR(100) | 불가 | 등록 담당자 식별값 |
| created_at | TIMESTAMPTZ | 불가 | 등록 시각 |

- 기본 키: `id`
- 외래 키: `restaurant_id → restaurants(id)`
- 실제 납품 예정일은 현재 명제에 없으므로 추가하지 않는다. 등록 시각을 예정일로 해석하지 않는다.
- 예정의 수정·취소 정책은 미정이다. 이 구조는 최초 등록 내용을 표현하며, 변경 이력까지 해결하지 않는다.

## 2. outbound_plan_items

술어:

> 납품 예정 `outbound_plan_id`에는 상품 `product_id`를 수량 `planned_quantity`, 단위 `uom`만큼 납품할 예정 항목 `id`가 포함되어 있다.

| 열 | 형식 | NULL | 의미 |
| --- | --- | --- | --- |
| id | BIGINT | 불가 | 예정 항목 식별자 |
| outbound_plan_id | BIGINT | 불가 | 소속 예정 |
| product_id | BIGINT | 불가 | 상품 |
| planned_quantity | NUMERIC(19,5) | 불가 | 예정 수량 |
| uom | VARCHAR(20) | 불가 | 수량 단위 |

- 기본 키: `id`
- 외래 키: `outbound_plan_id → outbound_plans(id)`
- 외래 키: `product_id → products(id)`
- 동일 상품을 여러 항목으로 구분할지는 미정이므로 `(outbound_plan_id, product_id)`에 유일 제약을 부여하지 않는다.
- 수량은 음수를 허용하지 않는 것을 기본 검증안으로 제안한다. 예정 항목에 0수량을 허용할지는 별도 결정한다.

## 3. outbound_reports

술어:

> `id`는 하나의 논리적 납품 완료 보고를 식별하며, `outbound_plan_id`가 있으면 그 예정의 수행 결과를 나타낸다.

| 열 | 형식 | NULL | 의미 |
| --- | --- | --- | --- |
| id | BIGINT | 불가 | 논리적 완료 보고 식별자 |
| outbound_plan_id | BIGINT | 가능 | 결과를 보고하는 예정 |

- 기본 키: `id`
- 외래 키: `outbound_plan_id → outbound_plans(id)`
- NULL이 아닌 `outbound_plan_id` 값은 전체 보고에서 유일해야 한다. 이 제약으로 예정 한 건에 별도 완료 보고 두 건이 연결되는 것을 막는다.
- NULL인 행은 여러 개 존재할 수 있어야 한다. 예정 없는 보고들을 하나로 취급하지 않는다.
- 논리적 보고 머리와 최초 보고 판은 함께 생성한다. 판이 없는 머리만 먼저 저장하여 예정이 마감된 것처럼 취급하지 않는다.
- 예정 연결은 보고 판 전체에 공통인 것으로 모델링했다. 잘못 연결한 예정을 나중에 정정하는 정책은 아직 다루지 않는다.

예정 없는 납품에는 현재 합의된 자연 업무 키가 없다. 따라서 새 `id`로 재전송한 같은 납품을 이 릴레이션만으로 중복 판정할 수 없다. 요청 재시도 식별과 실제 업무 중복 식별은 구분하여 후속 설계한다.

## 4. outbound_report_revisions — 정정 원칙 채택 시

술어:

> 담당자 `reported_by`가 시각 `reported_at`에 논리적 보고 `outbound_report_id`의 `revision_no`번째 판 `id`를 보고했으며, 식당 `restaurant_id`에 납품했다고 보고했다. 이전 판이 있으면 이 판은 `previous_revision_id`를 정정한다.

| 열 | 형식 | NULL | 의미 |
| --- | --- | --- | --- |
| id | BIGINT | 불가 | 보고 판 식별자 |
| outbound_report_id | BIGINT | 불가 | 논리적 보고 |
| revision_no | INTEGER | 불가 | 1부터 시작하는 판 번호 |
| previous_revision_id | BIGINT | 가능 | 바로 이전 판 |
| restaurant_id | BIGINT | 불가 | 실제 납품했다고 보고한 식당 |
| reported_by | VARCHAR(100) | 불가 | 보고 담당자 식별값 |
| reported_at | TIMESTAMPTZ | 불가 | 보고 접수 시각 |

- 기본 키: `id`
- 후보 키: `(outbound_report_id, revision_no)`
- 외래 키: `outbound_report_id → outbound_reports(id)`
- 외래 키: `previous_revision_id → outbound_report_revisions(id)`
- 외래 키: `restaurant_id → restaurants(id)`
- `revision_no >= 1`
- 1판은 이전 판이 없고, 2판부터는 같은 논리적 보고의 바로 앞 판을 참조한다.
- NULL이 아닌 `previous_revision_id`는 유일해야 한다. 하나의 이전 판에서 정정 판이 갈라지지 않는다.
- 예정 납품처와 보고 납품처는 각각 계획과 보고된 결과다. 예정에서 보고 납품처를 자동으로 도출하지 않는다. 서로 다를 때의 접수 정책은 후속 결정한다.
- 실제 수행 시각은 이 열에 섞지 않는다. 별도 기록 여부는 미정이다.

## 5. outbound_report_items — 식당 인계 보고 기준

술어:

> 보고 판 `outbound_report_revision_id`에는 상품 `product_id`를 수량 `delivered_quantity`, 단위 `uom`만큼 납품했다고 보고한 항목 `id`가 포함되어 있다.

| 열 | 형식 | NULL | 의미 |
| --- | --- | --- | --- |
| id | BIGINT | 불가 | 해당 판의 보고 항목 식별자 |
| outbound_report_revision_id | BIGINT | 불가 | 항목을 포함하는 정확한 판 |
| product_id | BIGINT | 불가 | 상품 |
| delivered_quantity | NUMERIC(19,5) | 불가 | 납품했다고 보고한 수량 |
| uom | VARCHAR(20) | 불가 | 수량 단위 |

- 기본 키: `id`
- 외래 키: `outbound_report_revision_id → outbound_report_revisions(id)`
- 외래 키: `product_id → products(id)`
- 동일 상품의 항목 구분 기준이 미정이므로 상품별 유일 제약은 두지 않는다.
- 예정 항목 참조는 아직 추가하지 않는다. 상품만으로 예정 항목과 일대일 대응한다고 가정하지 않는다.
- 음수는 허용하지 않는 것을 기본 검증안으로 제안한다. 0수량 항목 및 전량 미납 보고를 접수할지는 미정이다.

## 6. outbound_withdrawal_items — 위치별 반출 근거

술어:

> 보고 항목 `outbound_report_item_id`에 대해, 담당자는 그 항목의 상품을 위치 `location_id`에서 수량 `quantity`, 단위 `uom`만큼 반출했다고 보고했다.

| 열 | 형식 | NULL | 의미 |
| --- | --- | --- | --- |
| id | BIGINT | 불가 | 반출 내역 식별자 |
| outbound_report_item_id | BIGINT | 불가 | 소속 보고 항목 |
| location_id | BIGINT | 불가 | 반출 위치 |
| quantity | NUMERIC(19,5) | 불가 | 반출 수량 |

- 기본 키: `id`
- 외래 키: `outbound_report_item_id → outbound_report_items(id)`
- 외래 키: `location_id → locations(id)`
- 상품과 단위는 소속 보고 항목에서 결정된다. 같은 사실을 중복 저장하지 않는다.
- `quantity > 0`을 실제 반출 내역의 검증안으로 제안한다. 반출하지 않은 위치를 0수량 행으로 만들지는 않는다.
- 같은 보고 항목·위치의 반출은 합산한 한 행으로 표현하는 설계안을 제안한다. 이를 채택하면 `(outbound_report_item_id, location_id)`가 후보 키다.
- 서로 다른 위치에서 반출하면 위치마다 행을 둔다.
- 납품 수량과 반출 수량 합계의 일치 제약은 아직 두지 않는다. 그렇다고 차이가 있는 보고를 무조건 접수한다는 뜻은 아니다. 차이 처리 정책이 필요하다.

## 보고 전체의 무결성과 처리 경계

정정 및 원자적 재고 반영 제안을 채택할 때 적용할 규칙이다.

- 보고 판과 그 판의 전체 항목·반출 내역을 함께 접수한다. 일부만 접수하지 않는다.
- 보고 판과 항목·반출 내역은 수정하거나 삭제하지 않는다. 정정은 전체 내용을 가진 새 판을 추가한다.
- 정정 접수 시 논리적 보고를 기준으로 동시 처리를 직렬화하고, 요청이 바로잡는 판이 현재 판인지 확인한다.
- 보고 접수와 재고 반영은 함께 성공하거나 함께 실패한다.
- 정정 시에는 새 판 전체 반출 수량을 기존 차감 위에 다시 차감하지 않는다. 이전 유효 판의 반영과 새 판의 반영 사이의 차이를 재고 영역에서 처리한다.
- 실제 수행한 추가 납품은 정정 요청이 아니라 새 논리적 보고로 접수한다.
- 기준 정보 참조가 유효한지 검증한다. 삭제로 과거 보고의 참조가 사라지지 않도록 제한한다.
- 전산재고 부족을 이유로 보고를 거절할지는 여기서 정하지 않는다. 현장 결과 접수와 불일치 처리 정책이 선행되어야 한다.

선후 판의 동일 보고 소속과 연속 번호 등 여러 행에 걸친 조건은 외래 키만으로 모두 해결되지 않는다. 복합 제약 또는 접수 트랜잭션 검증으로 보장한다.

현재 유효한 판은 논리적 보고별 가장 큰 `revision_no`로 판정한다. 별도의 현재 상태 열은 이 초안에 두지 않는다.

## 재고 영역에 제공하는 근거

```text
논리적 완료 보고 ID
완료 보고 판 ID
반출 내역 ID
상품 ID
위치 ID
반출 수량과 단위
정정인 경우 이전 보고 판 ID
```

상품과 단위는 반출 내역이 속한 보고 항목에서 얻는다. 보고 관계에 행이 존재한다는 사실만으로 재고 반영의 실행 이력이 모두 표현되지는 않는다. 재고 영역이 정확한 보고 판·반출 내역을 반영 근거로 식별할 수 있어야 한다. 구체적인 재고 릴레이션은 이 문서의 범위 밖이다.

## 시나리오 대입

| 사례 | 표현 |
| --- | --- |
| 예정 없이 당근 7kg 납품 | 예정 참조가 없는 보고 머리, 최초 판, 당근 납품 항목과 반출 내역 |
| 예정 10kg, 실제 7kg | 예정 항목 10kg과 연결된 보고 항목 7kg을 각각 보존. 잔량 행은 생성하지 않음 |
| 위치 A에서 4kg, B에서 3kg 반출 | 납품 항목 하나 아래 반출 내역 두 행 |
| 같은 예정에 두 번째 완료 보고 | NULL이 아닌 예정 참조의 유일성 제약으로 거절 |
| 7kg 보고를 6kg으로 정정 | 같은 논리적 보고에 2판과 전체 항목·반출 내역 추가. 1판은 보존 |
| 마감 후 3kg 추가 납품 | 새 논리적 보고. 기존 마감된 예정에는 연결하지 않음 |

이 대입은 구조가 사례를 표현할 수 있는지 확인한 것이다. 미정인 업무 정책이나 실제 데이터베이스 동작을 검증한 것은 아니다.

## 아직 해결하지 않은 경계

- 창고 반출까지만 보고한다면 납품 수량을 없애고 위치별 반출 내역을 중심으로 단순화할 수 있다.
- 식당 인계 기준을 유지하면 반출과 인계 사이의 재고 반영 지연, 운송 손실·미인수 물품 처리 범위를 정해야 한다.
- 예정 수정 이력을 보존해야 한다면 예정 판과 완료 보고가 기준으로 삼은 예정 판의 관계가 추가로 필요할 수 있다. 현재 예정 값을 덮어쓰면서 과거 예정 대비 차이가 보존된다고 주장할 수 없다.
- 예정과 보고의 항목 연결, 상품 대체·초과 납품·납품처 변경의 접수 정책은 미정이다.
- 예정 없는 납품의 업무 중복 판정 기준은 미정이다.
- 전량 미납, 빈 보고, 예정 취소, 잘못된 예정 연결의 정정은 미정이다.

## 만들지 않는 릴레이션

- 피킹·운송 등 보고받지 않는 작업 상태
- 예약 재고와 작업 지시
- 예정 대비 미납 잔량과 자동 후속 납품 의무
- 식당 내부 재고와 조리 소비
- 재고 실사·조정의 내부 구조

별도의 출고 작업 객체는 만들지 않는다. `outbound_reports`는 현장 작업 상태가 아니라 하나의 논리적 보고와 그 정정 판들을 묶는 식별자다.
