# 운영 게시판, 공지 전파와 캘린더 시나리오

## 범위

공급사, 창고와 식당 사이에서 입고·출고와 창고 운영에 필요한 정보를 게시하고 대상에게 전달하며, 날짜가 있는 운영 정보를 캘린더에서 확인하는 업무를 다룬다.

이 문서의 `업스트림`과 `다운스트림`은 공급망에서 물품과 정보가 흐르는 방향을 설명하는 용어다. DDD의 컨텍스트 매핑에서 모델 의존 관계를 나타내는 업스트림·다운스트림을 뜻하지 않는다.

현재 공급망은 다음과 같이 본다.

```text
공급사 → 창고 → 식당
        물품의 다운스트림 방향

공급사 ← 창고 ← 식당
        공급망의 업스트림 방향으로 전달되는 정보
```

방향은 메시지 작성자의 고정 속성이 아니라 작성자와 수신자의 공급망상 관계에서 정해진다. 예를 들어 창고가 식당에 보내는 납품 변경 공지는 다운스트림 전파이고, 식당이 창고에 보내는 휴무 안내는 업스트림 전파다.

## 업무 사실

- 운영 게시글은 작성자가 특정 운영 정보를 기록하고 공유한 내용이다.
- 공지는 수신 대상에게 반드시 전달할 운영 게시글이다.
- 게시글의 작성 조직, 작성자, 작성 시각과 전달 대상을 확인할 수 있어야 한다.
- 하나의 공지를 업스트림 또는 다운스트림의 하나 이상의 대상에게 전달할 수 있다.
- 전달 방향만으로 수신 대상을 추론하지 않고 실제 대상 조직이나 그룹을 명시한다.
- 날짜가 있는 공지는 운영 일정과 연결하여 캘린더에서 볼 수 있다.
- 게시글 전달은 입고·출고·재고 보고를 대신하지 않는다. 공지에 수량을 적었다고 재고가 바뀌지는 않는다.

## 게시글과 공지

작성자는 제목, 본문, 작성 조직과 전달 대상을 지정하여 운영 게시글을 등록한다. 공지로 발행할 때에는 게시 시각과 필요한 경우 게시 종료 시각을 정한다.

전달 대상은 전체 운영자, 특정 공급사, 특정 식당 또는 업무상 정의한 대상 그룹이 될 수 있다. 공급사나 식당 사용자가 시스템에 직접 접속하지 않는 운영 방식이라면 내부 담당자가 외부에서 전달받은 내용을 출처와 함께 등록할 수 있다.

공지 발행과 대상별 전달 기록은 구분한다. 시스템은 공지가 누구에게 전달 대상이었는지 확인할 수 있어야 한다. 실제 열람 여부를 추적할지는 후속 설계에서 정한다.

## 공급망 방향별 전파

### 다운스트림 전파

공급망의 상류 주체가 하류 주체에 영향을 주는 정보를 전달한다.

- 공급사가 창고에 입고 지연이나 공급 중단을 알린다.
- 창고가 식당에 납품 일정 변경이나 품절 가능성을 알린다.
- 필요한 경우 창고가 공급사 공지를 해석하거나 대상을 좁혀 식당에 다시 전파한다.

다시 전파한 공지는 원문 또는 원래 공지를 식별할 수 있어야 한다. 다시 전파하는 과정에서 내용을 바꾸었다면 원문과 현재 전달 내용을 모두 구분할 수 있어야 한다.

### 업스트림 전파

공급망의 하류 주체가 상류 주체의 계획에 영향을 주는 정보를 전달한다.

- 식당이 창고에 휴무나 수령 불가 일정을 알린다.
- 창고가 공급사에 입고 가능 시간 변경이나 반복되는 품질 문제를 알린다.
- 필요한 경우 창고가 여러 식당에서 받은 정보를 취합하여 공급사에 전달한다.

업스트림 전파도 구체적인 수신 대상을 명시하며, 정보가 공급망 전체에 자동 공개된다고 간주하지 않는다.

## 운영 일정과 캘린더

날짜가 필요한 게시글은 운영 일정과 연결할 수 있다. 일정에는 제목, 시작 시각, 필요한 경우 종료 시각, 시간대, 관련 공지와 대상이 포함된다.

예시는 다음과 같다.

- 재고 실사 기간
- 창고 휴무 또는 운영시간 변경
- 공급사의 납품 불가 기간
- 식당의 휴무 또는 수령 불가 기간
- 예정된 시스템 점검

캘린더는 등록된 운영 일정을 날짜별로 보여주는 조회 수단이다. 공지에 연결된 일정을 선택하면 근거가 된 공지를 확인할 수 있어야 한다.

일정을 변경하거나 취소하면 공지와 캘린더가 서로 다른 내용을 보여주지 않아야 한다. 취소된 일정은 삭제하기보다 취소 사실과 시각을 확인할 수 있게 남긴다.

현재 출고 문서의 납품 예정에는 납품 예정일을 저장하지 않는다. 따라서 기존 납품 예정은 자동으로 캘린더 일정이 되지 않는다. 납품 예정일을 캘린더에 표시하려면 출고 영역에서 예정일을 업무 사실로 추가하기로 먼저 결정해야 한다.

## 외부 캘린더 연동

운영 일정은 사용자가 쓰는 외부 캘린더에서 구독하거나 개별 일정으로 추가할 수 있다. 외부 캘린더는 운영 일정의 복사본을 표시하며, 시스템에 등록된 운영 일정이 원본이다.

- 사용자는 자신에게 전달된 일정만 구독하거나 내보낼 수 있어야 한다.
- 일정 변경과 취소가 구독 캘린더에 반영될 수 있도록 일정의 안정적인 식별자를 유지한다.
- 외부 캘린더에서 내용을 수정한 결과를 시스템 원본에 반영하는 양방향 동기화는 현재 범위에 포함하지 않는다.
- 접근 권한이 사라진 대상에게 이후 비공개 변경 사항이 계속 노출되지 않도록 구독 권한 정책이 필요하다.

## 수정, 정정과 철회

아직 발행하지 않은 게시글은 수정하거나 삭제할 수 있다. 발행한 공지는 당시 전달한 내용을 확인할 수 있도록 변경 이력을 남긴다.

- 내용 오류는 새 판으로 정정하고 현재 판을 다시 전달한다.
- 더 이상 유효하지 않은 공지는 철회하되 과거 발행 사실을 남긴다.
- 일정 변경과 취소는 연결된 공지의 현재 내용과 함께 전달한다.
- 다시 전파한 공지의 원문이 정정되었을 때 자동으로 재전파할지 담당자 확인을 거칠지는 후속 설계에서 정한다.

## 시나리오

### 1. 공급사의 지연 공지를 다운스트림으로 전파하는 경우

1. 공급사가 창고에 특정 상품의 입고 지연을 알린다.
2. 창고 담당자가 출처와 원문을 확인할 수 있게 운영 공지로 등록한다.
3. 영향을 받는 식당을 전달 대상으로 선택하여 다운스트림으로 다시 전파한다.
4. 각 수신자는 자신에게 전달된 공지와 원문 관계를 확인한다.

### 2. 식당 휴무 정보를 업스트림으로 전달하는 경우

1. 식당이 특정 기간에 물품을 받을 수 없다고 창고에 알린다.
2. 창고 담당자가 해당 식당과 기간을 담은 공지를 등록한다.
3. 공지는 공급망의 업스트림 방향으로 창고의 출고 운영 담당자에게 전달된다.
4. 공지 자체는 기존 납품 예정이나 출고 보고를 자동으로 수정하지 않는다.

### 3. 실사 일정을 캘린더에 표시하는 경우

1. 담당자가 창고 전체 실사 공지를 작성하면서 시작·종료 시각을 등록한다.
2. 공지를 대상 운영자에게 발행한다.
3. 시스템은 연결된 운영 일정을 공유 캘린더에 표시한다.
4. 사용자는 일정에서 실사 공지 원문을 연다.

### 4. 운영 일정을 변경하는 경우

1. 담당자가 실사 날짜가 바뀐 사실을 확인한다.
2. 기존 공지의 새 판과 변경된 일정을 발행한다.
3. 시스템은 변경 사실을 대상에게 다시 전달하고 내부 및 외부 구독 캘린더에 반영한다.
4. 과거 날짜와 변경 시각은 이력으로 확인할 수 있다.

### 5. 공지를 철회하는 경우

1. 담당자가 잘못 발행한 휴무 공지를 철회한다.
2. 시스템은 대상에게 철회 사실을 전달한다.
3. 연결된 일정은 취소로 표시하고 과거 발행 기록을 보존한다.

## 현재 범위에서 다루지 않는 내용

- 식당 내부의 근무 일정, 조리 일정과 재고 일정
- 공지 내용만으로 입고·출고·재고 데이터를 자동 변경하는 기능
- 채팅, 화상 회의와 일반 사내 메신저
- 외부 캘린더에서 시스템으로 변경 내용을 받아들이는 양방향 동기화
- DDD 컨텍스트 사이의 업스트림·다운스트림 관계 정의

## 개발자에게 위임하는 판단과 후속 범위

- 외부 공급사와 식당 사용자가 직접 로그인할지, 내부 담당자가 대신 등록할지에 대한 사용자 모델
- 게시글과 공지를 별도 객체로 둘지 게시 상태와 전달 정책으로 구분할지 여부
- 조직, 개인과 그룹을 포함한 전달 대상 및 권한 모델
- 열람 확인, 알림 채널과 재전송 정책
- 원문 재전파와 정정 전파의 자동화 범위
- 외부 캘린더 구독 형식과 접근 만료 방식
